# AGENTS.md

## Project Shape

This repository contains Maker Track Studio, a local-first 3D printing cost
tracker distributed as a Windows/Linux desktop app and an optional LAN-only
self-hosted browser app.

- `apps/desktop`: Wails entry point, desktop packaging, release artifacts and smoke tests.
- `apps/api`: shared Go/Gin/GORM backend, SQLite initialization, cost logic and backups.
- `apps/web`: React/Vite UI embedded in Desktop and served by the Self-Hosted distribution.

There is one application and one SQLite database. The desktop app still talks to
the embedded backend over loopback HTTP at `127.0.0.1:8080`. Self-Hosted exposes
browser access only through the authenticated HTTPS reverse proxy on a trusted LAN.

## Post-Refactor Guardrails

- Do not introduce public Internet hosting, PostgreSQL, user accounts, sessions, Swagger generation, duplicated generated bindings, or tracked build binaries without an explicit requirement.
- Preserve SQLite data compatibility, backup export/import, and recovery flows.
- Keep all business operations available in the local desktop application.
- Keep the backend bound to loopback and CORS restricted to known Wails/development origins.
- UUIDs are generated by Go model hooks, not by database extensions.

## Development Commands

Backend:

```bash
cd apps/api
go test ./...
go vet ./...
```

Frontend:

```bash
cd apps/web
npm ci
npm run lint
npm test
npm run build
```

Visual documentation screenshots (install Chromium once per machine or CI runner):

```bash
cd apps/web
npm run screenshots:install
npm run screenshots
```

Desktop development on Linux:

```bash
cd apps/desktop
go run github.com/wailsapp/wails/v2/cmd/wails@v2.12.0 dev -tags webkit2_41
```

On Windows, omit `-tags webkit2_41`.

## Reusable Agent Workflows

- When asked to implement a GitHub issue end-to-end, follow `.agents/prompts/implement-issue.md` in addition to this file.
- Treat `AGENTS.md` as the repository-specific source of truth when it conflicts with generic instructions in a reusable prompt.

## Implementation Expectations

- Read adjacent code before changing behavior and follow existing patterns.
- Keep changes narrowly scoped to the requested workflow.
- For persisted data changes, use additive SQLite-compatible migration thinking and include backup/rollback considerations.
- Keep API model, DTO, handler, route, frontend service, and page expectations in sync.
- For React forms, prefer existing `react-hook-form` + `yup` patterns and show user-facing errors with existing toast/error handling.
- For a visible UI change, update the affected deterministic Playwright scenario in `apps/web/visual` and regenerate its tracked image in `docs/screenshots`. Do not use a real database, customer data, backup, or local filesystem path in a screenshot fixture or image.
- For cost logic, check app config values and print-job/filament relationships carefully.
- Apply the local `security-review` skill checklist when changing handlers, routes, DTOs, database queries, file I/O, external calls, or React forms.
- Run the smallest relevant check set before finishing. If a platform-specific check cannot be run locally, say so clearly.

## Specialist Lenses

Use these lenses when planning or reviewing work:

- Desktop/runtime: Wails startup, embedded API lifecycle, loopback behavior, SQLite paths, packaging outputs, smoke tests and release artifacts.
- Frontend/product: desktop UI workflows, forms, validation, loading/empty/error states, API service contracts and accessibility basics.
- Migration/compatibility: post-refactor boundaries, SQLite data compatibility, backup/import behavior, env var compatibility and docs drift.
- Data: schema, GORM models, SQL/query behavior, backfills and data quality checks.
- Quality: regression risks, API/frontend contract mismatches, focused tests and release readiness.

## Code Review Rules

- Flag any change that revives removed architecture unless the user explicitly asked for it.
- Flag schema, backup/import or env var changes that lack compatibility and rollback reasoning.
- Flag API response changes that are not reflected in frontend services/tests.
- Flag forms that submit unvalidated numeric cost inputs or render raw error objects.
- Flag UI changes that alter a documented screen or meaningful interaction without updating its visual catalogue scenario and image.
- Flag desktop packaging changes that only verify source builds and skip artifact behavior.
